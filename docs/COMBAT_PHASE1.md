## 配置与数据所有权

`config.toml`：

```toml
[combat]
controlled = "infantry_health_cooling"
target = "infantry_health_cooling"
```

`controlled` 选择红方训练车，`target` 选择蓝方小装甲假人。英雄假人保持固定预设。
省略 `[combat]` 使用默认配置；预设字符串仅接受上表五种训练预设，字段名不接受拼写错误。

每个机器人根实体独占 `RobotIdentity` 和 `RobotCombatState`：

- 稳定 ID 是场景槽位：训练车 1、小装甲假人 2、英雄假人 3，不是裁判编号或视觉标签。
- `RobotIdentity` 固定队伍、角色、ID；调试切换贴纸不修改身份或规则。
- `RobotCombatState` 持有规则快照和独立的发射机构、热量、额度、生命状态。
- 资产加载完成后，底盘、云台、装甲及其子节点通过 `RobotMember` 指向根实体与稳定 ID。
  这些引用供后续发射与伤害模块使用；不为装甲复制血量或热量。
- 资产装甲根就绪时校验归属并输出日志；非机器人目标不建立机器人归属。

规则在生成机器人时从配置复制。配置热更新只暂存新的选择，不更改现有机器人的身份、
装甲外观或规则快照。修改配置后按 R 即可在新回合统一应用；回合中不直接改变这些战斗参数。
当前 Talos v6 的 target ID 仍沿用原有实体编号，新稳定 ID 将在模块 6 中统一接入。

## 模块 2：统一发射与实际出膛

### 配置与规则边界

继续使用已有 `projectile.speed`、`projectile.cooldown` 字段，新增可省略的
`projectile.launch_delay_s`：

```toml
[projectile]
# 下列片段只列出发射机构参数，其余弹丸字段沿用仓库示例。
speed = 25.0
cooldown = 0.05
launch_delay_s = 0.0
```

- `speed` 是相对于枪口的发射速度，单位 m/s，必须有限、正值且不超过 25。
  上限来源为 RMUL 2026 V1.2.0 §3.1.2–3.1.3，表 3-3/3-4，第 18–20 页。
  保留原有底盘平移速度叠加；世界系速度可能大于枪口相对速度，不实现超弹速锁定。
- `cooldown` 是模拟机械最小出膛间隔，单位秒，默认 0.05；必须为可表示的有限正时长。
  不将其称为 RM 裁判规则。纳秒精度下舍入为零的间隔也拒绝应用。
- `launch_delay_s` 是额外供弹至出膛延迟，默认 0，必须为可表示的有限非负时长。
  它独立于既有 `gimbal_actuator.command_delay_s`，同样属于仿真机械参数。
- 这三个参数在生成机器人时复制到每车发射机构。热更新有效值只暂存到下次场景初始化；
  模块 7 接入后可按 R 在新回合应用。非法热更新拒绝整个配置，保留当前配置与状态。
  主程序启动时要求工作目录中的 `config.toml` 可读取、可解析且通过校验；失败打印
  `Cannot apply config.toml: ...` 并退出，不启动使用另一套默认射击参数的场景。

### 请求、时钟与出膛

`combat::shooting::request_fire` 是所有 17 mm 输入的唯一入口。键盘与手柄先合并到
`ControllerState`，长按每隔机械间隔提交一次尝试；松开再按也不能绕过上次实际出膛间隔。
Talos 保留 `fire_advice` 上升沿语义：持续高电平只提交一次；每个已接收且生效的上升沿
独立提交，取消一帧累计上升沿后按数量批量生弹的路径。

输入采样在 `PreUpdate` 中完成；发射结算在 `FixedPostUpdate`、Avian 物理准备之前执行。
机械间隔、供弹截止时间与出膛时间统一使用 `Time<Fixed>` 的仿真时钟。截止时间向后对齐
到实际物理步边界，例如 7 ms 物理步下，50 ms 的机械间隔最早在 56 ms 后满足。
配置热更新使用 `set_timestep_hz`，保留累计仿真时间，不把出膛时钟重置为零。

同一步先处理到期的已受理供弹，再按 FIFO 处理新请求。请求队列上限 256；同一机器人
同一时刻最多出膛一发。多条输入在同一帧积累后，第一条可能成功，其余按当时状态拒绝，
不会按照历史命令时间重建过去的出膛，也不会将拒绝请求存到冷却结束后补射。

额外延迟非零时，每车最多保留一发已经受理的供弹请求；供弹中返回 `FeedBusy`。
这条延迟请求只有到期才再次校验并读取枪口姿态。关闭外部控制会拒绝未出膛的 Talos 请求，
已经出膛的弹丸不受影响。热量限制已在模块 3 接入，生命限制已在模块 5 接入；额度仍待模块 4。

Talos 的命令接收、既有命令延迟和云台积分仍使用原有墙钟；这次没有将整条控制链改为
固定步进。Talos 请求生效至下一个物理步存在调度延迟，不宣称链路已支持加速或完全复现。

### 事件与统计

每条请求有独立 ID、机器人 ID、来源和仿真请求时间；Talos 来源额外保存命令原始时间戳
用于关联。结果通过 Bevy `FireRequestResult` 消息和日志提供：

| 结果 | 含义 |
| --- | --- |
| `Feeding` | 已受理、等待明确配置的供弹延迟，尚未计入发射数 |
| `Fired` | 已创建弹丸，包含弹丸唯一 ID |
| `Rejected` | 附带 QueueFull、UnknownRobot、NoShooter、MechanicalInterval、FeedBusy、ExternalControlDisabled、MissingMuzzle、InvalidMuzzlePose；模块 3 新增 HeatCoolingLock、HeatRoundLock，模块 5 新增 Dead |

每颗实际 17 mm 弹丸携带 `ProjectileShot`，记录弹丸 ID、原始请求/发射者、仿真出膛时间、
枪口世界位姿与初速度。枪口位姿读取完整模型层级和当前刚体物理位置，包括底盘、云台及
枪口的平移偏置；修正旧生弹路径忽略中间层级平移、依赖缓存云台变换的问题。
世界坐标沿用 Bevy 的 Y 向上，长度为米、速度为 m/s。不增加云台转动切向速度模型。

生弹、每车 `actual_shots` 计数、现有全局发射计数、`ShotFired` 消息按顺序执行。
拒绝和仅进入供弹均不算实际出膛；手柄震动也只跟随实际出膛。
消息仅使用 Bevy 的短时消息缓冲，尚未提供模块 6 的持久评估缓存或 v7 遥测；当前 Talos v6
继续发布现有实际发射累计数。飞镖及其统计不通过本模块入口。
可选 ROS2 适配器同步改为提交统一请求，保留其原有 10 Hz 输入限速，不再调用已移除的
旧生弹函数；本次主要验收后端为 Talos。

## 模块 3：热量结算与锁定

### 规则与数值

依据同一官方 V1.2.0 手册 §3.3.1.3「射击热量超限和冷却」，第 29–30 页、图 3-10。
仅对本阶段的 17 mm 发射机构应用：

| 条件/事件 | 结算 |
| --- | --- |
| 实际出膛一发 | 当前热量增加 10，与初速度无关 |
| 每个 100 ms 冷却截止时刻 | 减去预设冷却速率的十分之一，最低为零 |
| 热量恰好等于普通上限 | 不新增锁定；已有锁定继续保持 |
| 热量超过普通上限 | 设置 `cooling_locked`，降回上限以下仍不能发射 |
| 热量冷却至零 | 只解除 `cooling_locked` |
| 热量达到上限＋100 | 设置 `round_locked`，本局不解除，冷却至零也不能发射 |

正文对整局锁定使用 `Q1 > Q2`，图 3-10 使用 `Q1 ≥ Q2`。按既定方案采用流程图的 **`≥`**，
保留这项差异说明。两个锁定状态分别保存；同时存在时，发射请求优先返回 `HeatRoundLock`。
解除普通热量锁定不修改整局锁定、机械间隔或外部控制开关。

热量内部使用十分之一单位的整数；预设上限、冷却速率使用整数规则单位。
例如冷却优先步兵每次减 2.4、爆发优先每次减 1.4、哨兵每次减 3.0，均可精确结算，
不会因浮点尾差在上限等号或零点多锁定/少冷却一拍。`HeatState::current()` 返回用于
展示的规则热量值，转换不参与规则判断。没有新增规则热更新或主动预留热量配置。

### 确定的处理顺序

每个物理步的统一发射入口依次执行：

1. 对每台有 17 mm 发射机构的机器人，结算所有已到期的 100 ms 冷却刻度并更新普通解锁。
2. 检查已有供弹请求和新请求的发射条件。热量锁定期间直接拒绝，且取消尚未出膛的供弹。
3. 创建实际弹丸并计数，然后立即增加 10 热量并设置新增锁定，再处理下一条请求。

热量尚未锁定时允许发射使热量越过上限的那一发，随后锁定；不以“剩余热量不足 10”
提前拦截。仅请求被受理、等待供弹、机械间隔拒绝或热量拒绝都不会增热。
冷却至零的同一物理步可以受理新请求；新出膛弹丸的热量不会再被本步已经结算的冷却扣除。
此前已经拒绝的请求不会在解锁后补射。

各车独立保存热量、锁定和最后冷却刻度，继续使用 `Time<Fixed>`。
每个场景初始热量为零，第一拍在仿真时间 0.1 秒；按固定的 100 ms 刻度推进，
不会将渲染帧的耗时直接乘上冷却速率。一次物理步跨过多个冷却刻度时按顺序补齐，
相同仿真时刻的冷却结果不依赖画面帧率。零热量期间仍推进刻度，不积累未来可用的冷却量。
后续场景重置可通过 `HeatState::new(当前仿真时间)` 创建新的热量状态与冷却起点；
模块 3 初次验收时需重启清除整局锁定；模块 7 接入后可通过 R 场景重置清除。

当前模型每发出膛后立即应用普通锁定，所以正常逐发路径不会自然累积到上限＋100。
整局锁定仍完整实现，通过受控初态的确定性测试验证边界；不为演示该状态增加绕过
普通锁定的发射路径，也不宣称复现了真实裁判检测延迟导致的超发。

## 模块 5：装甲伤害、战亡与血条

规则依据：RMUL 2026 3V3 V1.2.0 §3.3.1.1 表 3-7，第 29 页，17 mm 原始伤害为 20 HP。
第 28 页的法向速度门槛和装甲检测间隔按已确认的训练简化不实现；不额外加入撞击扣血、
友军伤害、复活或实际弹仓。允许发弹量模块尚未实现，仍为无限允许发弹量。

### 首次接触与伤害结算

- 17 mm 弹丸使用 `ProjectileShot` ID 标识，在物理步结束处理首次实体接触；实际消耗后
  立即移除弹丸，同一步的其他碰撞体消息无法再次扣血。车体和环境命中只消耗弹丸。
- 原有装甲接触结束计数不再处理 17 mm；它仅保留非本阶段弹丸的旧计数路径。
  能量机关收到 17 mm 首次命中后仍走独立的机关激活逻辑，不接入机器人 HP；前哨站装甲
  仍可计接触，只有拥有机器人战斗状态的目标才会扣血。飞镖不产生本模块伤害事件。
- 每次命中存活机器人装甲，实际扣血为 `min(20, 剩余HP)`。残血 10 HP 目标的最后一发
  记为标称伤害 20、实际伤害 10。尸体装甲接触可计命中，但不再产生伤害或重复击毁。
- `ArmorContact`、`DamageApplied`、`RobotDied` 是独立短时 Bevy 消息，带弹丸 ID、机器人
  ID 和仿真时间；伤害消息另外保存标称/实际伤害及剩余血量。每车 `DamageStatistics`
  保存装甲接触、造成伤害的命中数、造成/承受的实际伤害和击毁数。模块 6 再接有界评估缓存。
- 装甲归属沿 `RobotMember` / `RobotIdentity` 和父子层级解析，不使用数字贴图标签。
  保留现有敌我碰撞层，伤害入口额外排除自己与同队机器人。

### 物理接触适配（不是新增比赛规则）

Avian 0.7 的 `CollisionStart` 包括预测接触：25 m/s 弹丸的默认预测范围可达约 0.4 m，
直接计命中会误把仍在空中的弹丸判为撞地。17 mm 弹丸因此使用零预测裕量及专用接触钩子，
过滤尚未真正接触的预测点，仅保留 0.1 mm 数值容差（在引擎既有碰撞边距之外）。这不是
力度或最低速度门槛；其他刚体和飞镖不使用该钩子。

同时启用扫掠 CCD。由于该版本内建 CCD 对子碰撞体的支持有限，物理步结束还会按弹丸从
上一物理位置到当前位置的球形扫掠，补充子装甲的首次接触并选取路径上最近的命中。
扫掠使用相同的双向碰撞层过滤、弹丸真实半径和本步碰撞体姿态，不把未来预测位置计作命中。
这是物理步内的几何近似，未实现移动目标的完整连续时间求解，也不声称整条视觉链路可加速复现。

原有车体支撑圆柱半径 0.2593615 m，而 GLB 装甲安装半径约 0.204–0.277 m；把原圆柱直接
用于拦弹会覆盖部分装甲。现保留原支撑碰撞体参与地面/车辆动力学，另在车内增加仅与敌方
弹丸碰撞的 `CombatBodyCore`：半径 0.17 m、高 0.231298 m，中心 Y=-0.115649 m，密度为零，
不改变车辆质量和惯量。该内核是训练用车体近似，不是精细车壳模型或官方规则尺寸。

### 战亡和显示

血量归零后，根实体及所属控制节点增加 `CombatDead`，停止底盘主动施力、底盘姿态驱动和
手动/远程云台驱动；保留刚体、碰撞体及已有线速度/角速度。清理该车待处理发射和供弹请求，
以 `Rejected(Dead)` 结束它们；新请求也不能发射。受控机器人战亡时清除 Talos 接收队列、
延迟队列与有效指令，关闭外部控制，后续控制输入不能在战亡期间重新启用发射或云台驱动。
ROS2 接收路径也会丢弃关闭控制或战亡时的命令。

战亡清零当前热量及普通热量锁，但保留整局锁。已出膛的其他弹丸继续飞行，即使发射者已
战亡仍可扣血。灯条使用独立非发光深色材质，原材质句柄保存在 `ExtinguishedLight` 中，
避免修改共享 GLB 材质导致其他机器人灯条一起熄灭。未来重置需恢复材质、移除战亡标记，
并恢复状态、清除本回合消息与统计；模块 7 已提供 R 重置入口完成这些恢复。

新增 `preview.health_hud = true`（兼容旧配置省略，启动时生效）。窗口右下角的

## 模块 7：场景重置与回合验收

### 操作和恢复范围

按 **R** 请求重置，实际恢复在下一次 FixedFirst 物理步开始时统一执行。连续重复请求合并；
模型尚未完成初始化时保留请求，等待所有机器人初始姿态齐备。公共入口为
`combat::reset::request_scene_reset(&mut World)`，后续训练接口可复用；当前没有 Gym/reset-step API。

恢复所有机器人的初始根节点位置/姿态、底盘与云台局部姿态、零速度、HP、生命状态、灯条、
热量和全部锁定原因。恢复启动时保存的允许发弹量状态；当前默认 Unlimited，Limited 尚未
接入发射扣减，不能据此宣称有限弹量可用。角色/规则和发射速度、间隔、供弹延迟使用当前
有效配置统一重建，外观标签同步匹配角色；非法发射配置拒绝应用，不部分重置。
初始位置取车辆模型就绪、首次物理步前的场景姿态，重置后车辆会正常落地。

清理在途 17mm 弹丸及飞镖、待处理发射请求和供弹状态、当前/延迟/接收控制命令、本回合
碰撞/战斗消息及统计。保留飞镖发射位置标记，前哨站/能量机关状态不在机器人回合重置范围。
恢复最初被选中的假人，停止两个底盘的持续旋转。Avian 的接触图和物理岛保持内部一致，
由正常的位姿更新和碰撞检测重建接触；不单独清空这些相互关联的引擎缓存。

重置关闭外部控制。键盘/手柄射击和自动瞄准扳机须先释放，再重新启用；控制器重新启用时
还会清除接收队列，拒绝启用前收到或生成的 Talos 命令。`R` 不修改视觉目标选择或火控算法。
全局 Fixed 时间以及弹丸、请求、事件和图像序列号保持递增；回合编号从 1 开始，回合时间
以当前 Fixed 时间减去本回合起点计算。

### 评估和图像边界

左下角帮助文字显示 `round`、回合 `sim` 时间和 R 提示。重置前输出一条 JSON `round summary`，
按机器人汇总实际出膛、装甲接触、有效伤害命中、有效伤害量、击毁、热量锁定次数和时长。
`heat_locks` 分别计入普通/整局锁定的进入次数；`heat_locked_s` 为任一热量锁定生效的时间并集，
两个原因同时存在不重复累计。持续到重置的锁定也计算到边界，战亡不会关闭仍生效的整局锁。

通过 `round_summary(&mut World)` 可以获取当前回合摘要。内存保留最近 32 条已结束回合摘要，
当前回合最多 1024 条带 ID、相对仿真时间和原因的事件，超出时淘汰最旧记录并累计
`dropped_events`；重置清空当前事件缓存。`combat.event_details = true` 在重置时额外打印这些
事件，不启动 MCAP 或创建长期录制文件。

Talos 图像快照在 Extract 阶段携带**内部**回合编号。GPU 回读后的发布和重置共用一把回合锁，
旧回合的异步快照完成后被丢弃，不会带着旧统计发布到新回合。开启
`RUST_LOG=warn,daedalus::robomaster::combat=info,daedalus::talos::capture=debug` 可核对
`round frame round=... frame=... timestamp_ns=...` 与 `scene reset` 的发布边界。

**与模块 6 的边界：**当前仍是 v6，未新增跨项目回合/血量遥测字段。重置前已经交付给
视觉程序的帧无法撤回，其旧时间戳仍属于旧回合；本模块也不清空视觉内部 tracker。
v6 命令没有来源帧编号，因此不能证明重置后新生成的命令一定基于新回合图像。
本模块保证模拟器队列隔离、重新启用时的新命令门槛，以及发布端不回流旧快照；
跨项目的显式回合归属和更严格的来源帧校验需由模块 6 升级协议后完成。
因此模块 4、6 仍未完成，不能宣布第一阶段全部完成或已经支持加速可复现训练步进。

## 模块 4 与模块 6：允许发弹量、Talos v7 和 Foxglove

允许量配置位于 `[combat]`，`controlled_allowance` 和 `target_allowance` 独立，默认均为
`{ mode = "unlimited" }`；有限示例 `{ mode = "limited", initial = 50 }`。
只建模允许发弹量，不建模弹仓、装填和兑换。实际生弹后扣减一发；零额度拒绝不生弹、
不增热、不增加实际发射统计。供弹等待和缺失枪口不会提前扣减。无限模式保留其余限制。
R 重置统一应用当前配置的初始额度，不再恢复启动时缓存的旧额度；三套场景默认无限。

v7 在图像快照中携带稳定机器人 ID、队伍、角色、生命、热量、上限、冷却、额度与
全部物理禁射原因。机器人位置真值使用同一个稳定 ID，装甲真值有 `owner_robot_id`；
非战斗对象不混入机器人生命结算。

`FixedLast` 在战斗结算后构造当前真值，并按 100 ms 截止点采样自身裁判状态。
时间来自 Fixed 仿真时钟，实际采样可晚一个物理步；每帧携带实际样本时间和序号，
重复样本不伪装成更新。R 后立即开始新回合样本，进程仿真时间、样本序号和事件 ID
继续递增。本回合计数（包括新增的拒绝请求数）清零。

视觉端两个按需 JSON 话题：`/referee/self` 仅含自身最近裁判样本；
`/simulation/combat/evaluation` 含当前机器人真值、统计及事件。伤害归因和敌方 HP
不进入正式算法或自身裁判话题。窗口 HUD 仍直接读物理状态，不加入采样延迟。

事件保留现有带原因和参与者的描述，新增装甲接触事件；模拟器缓存最近 1024 条，
每帧传最近 64 条，客户端必须按 ID 去重并检测跳号。`events_dropped` 仅计内部缓存
淘汰；传输窗口之外的遗漏不能据此排除。计数使用状态累计值，不从重复事件盲目累加。
每条描述最多 231 字节 UTF-8。事件缓存不是可靠消息队列或长期录像。

v7 `RobotCombatMeta=128`、`CombatEventMeta=256`、`CombatFrameMeta=18624`、
`CapturedFrameMeta=24768`、`ShmMetaRegion=74752` 字节；命令为 64 字节。
Rust 与 C++ 均有尺寸/偏移断言，先校验公共头的版本，再检查完整区大小。
命令携带来源图像的回合、序号与 epoch 采集时间；有效目标必须属于当前回合且来源时间
非零，并通过 F5 生成/接收时间门限。旧回合图像生成的新命令也会拒绝。
停止命令仍可安全停止；不改变正式预测/火控算法，也不重置视觉跟踪器的内部估计。
已经送入视觉线程的旧图像不能撤回，但其回合归属明确，旧命令不恢复开火。
